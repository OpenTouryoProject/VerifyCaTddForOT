# 受注一覧（OrdTf）・WebForms_Sample の仕様の決定

対象：[テスト仕様](./test3-testfirst-OrdTf-webforms-tests.md)（段 1 承認済み）。仕様：NorthwindDbSampleSpec@2240ab3（段 1 の承認時は 0b7e58a。決定 1 を DEC-CMN-07 として記録した版）。
段 1 では仕様の決定が無かった。決定 1 は、段 4 のレビューで見つかった（テスト仕様 5 章が `ERR-DB` を「確かめられない」としたことで見えていなかった）。
ケース1・ケース2 の決定は [mvc](./test3-testfirst-OrdTf-mvc-decisions.md)・[mvc-core](./test3-testfirst-OrdTf-mvc-core-decisions.md)。DEC-ORD-10・11 は記録済みで、ここでは再び問わない。

## 決定 1

- 仕様の ID：`ERR-DB`（共通仕様 7 節）、`EV-ORD-101`・`EV-ORD-102`・`EV-ORD-104` のエラーハンドリング
- 背景：共通仕様 7 節は `ERR-DB`（データベースへの接続・実行に失敗した）の動作を、
  「『データベースに接続できませんでした。時間をおいて再試行してください。』を表示し、画面の状態は変更しない」と決めている。
  「上記いずれにも当てはまらない例外は `ERR-DB` と同じ扱いとする」ともある。受注一覧の 3 つのイベントは、どれもエラーハンドリングに `ERR-DB` を挙げている。
  今の実装（ケース1・2・3 とも同じ作り）は、DB の失敗を捕まえず、基盤の異常終了の処理（親クラス 2）に任せている。
  利用者に見えるのは、同じ画面に文言が出て状態が保たれる姿ではなく、基盤のエラー画面（WebForms ではエラー画面への遷移）になるはずである。
  テストは、テストから DB を落とせない・接続文字列を壊す方法が共用の設定を汚すため、この場面を扱っていない（テスト仕様 5 章）。
  ケース1 の計画は「DB の失敗は基盤任せ（`ERR-DB` は範囲外）」と書いているが、範囲外と決めた記録は、決定記録にも対象の仕様（範囲外の列挙）にも無い。
- 問い：受注一覧で DB の失敗が起きたとき、どう振る舞うか。
- 選択肢：
  1. 定めない（実装に任せ、テストの期待にしない）。結果：今の実装（基盤任せ）のまま。テストも実装も増えない。仕様の `ERR-DB` の動作をこの範囲で満たすかは決まらず、後で別のケースで同じ問いが再び出る可能性がある。
  2. 基盤のエラー画面で代える。`ERR-DB` の文言と「画面の状態を変えない」は、この範囲では求めない。結果：今の実装のまま。利用者には基盤のエラー画面が出て、一覧の条件・ページは失われる。仕様（共通仕様 7 節）との食い違いが、決定として記録に残る。テストは増えない。
  3. `ERR-DB` のとおり、同じ画面に文言を出して状態を保つ。結果：P層で例外（`BusinessSystemException` など）を捕まえ、文言を出して一覧状態を変えない作りに変える。3 つのケースすべてで実装を変える。確かめるには、テストから DB の失敗を起こす手段（テスト用の差し替えなど）を決める必要があり、手間が大きい。
- 推奨と理由：1（定めない）。サンプルの利用者が通常する操作ではなく、DB を落とすテストの手段が今無い。選択肢 2 は、仕様の動作を「求めない」と決める点で 1 と同じだが、基盤のエラー画面を期待として残す分、後で食い違いを問われやすい。決めるなら 2。3 は手間が大きい。
- 影響するケース：ケース1（MVC_Sample）・ケース2（MVC_Sample_Core）にも同じ問いが出る。3 が選ばれたら、3 つのケースで実装を変え、テストを足す。
- 記録先：仕様の決定記録（`LLD/Decisions/Common.md`。全モジュールに効くため）
- 判断：GO（1。定めない）。2026-11-14 に人が選んだ。理由（人）：「DB 接続エラー」は「業務続行不可能なエラー」に分類され基盤に任せる処理で、「業務続行可能なエラー」の場合は後処理を実装できる。記録：NorthwindDbSampleSpec の `LLD/Decisions/Common.md` に DEC-CMN-07 として記録済み（版 2240ab3。索引の件数も 7）。出どころの欄は、DEC-ORD-10・11 と同じ `OpenTouryoProject/OpenTouryoCodingAgentAssets#17` とした
