# テスト先行：人の判断の代行（受け渡しの取り決め）

**このファイルは司令役が読む**（[司令役の手順](./cmn-testfirst.md)とあわせて）。OpenTouryoProject/OpenTouryoCodingAgentAssets#22 の検証だけで使う。
司令役の手順で「人に聞く・人に上げて止まる」とされていることのうち、下の表の「代行」の行は、**人に聞かずに、依頼のファイルを書いて代行役の答えを待つ**。
この取り決めと司令役の手順が食い違うときは、この取り決めに従う。

- 代行役：OpenTouryoCodingAgentAssets 上の、別の Claude Code のセッション。仕様と作者の過去の判断から決める。
- 代行の決定が妥当かは、受注管理（SC-ORD-01〜05）を作り終えた後に、人がまとめてレビューする（決定記録のブランチの PR）。
  そのため、代行が決めたことは、決定のレポートと決定記録に「**決めた者：代行**」と必ず書く。

## 代行するもの・しないもの

| 司令役の手順の箇所 | この取り決めでの扱い |
| --- | --- |
| 仕様の決定（手順 3。段 2 以降に出た決定も） | 代行。依頼 `decision` |
| 終わりの判断（手順 6） | 代行。依頼 `final`。目で見る確認と、確かめられない環境は、代行役が「人に回す」と答える |
| 決定記録の案を書いた後のコミット | 代行。依頼 `commit`。代行役がコミットして push し、答えに版を書く（「仕様が <版> に更新された」の合図を兼ねる） |
| 3 往復で承認されない差し戻し | 代行。依頼 `escalate`（続けるか・止めるか、どう直すか） |
| 検出器（commit-msg フック）がコミットを止め、正当な理由を書けない | 代行。依頼 `detector`。代行役は**テストを弱めない側**で答え、「要レビュー」を付ける |
| 最初のコミットの前のアカウントの確認 | 聞かない。司令役への指示に書いた答えを使う |
| 管理者の権限が要る操作（SQL Server・Docker の起動など） | 代行しない。**このセッションの人に上げて止まる**（司令役の手順のまま） |
| push が資格情報で失敗したとき | 代行しない。人に `! git push` を頼んで止まる（司令役の手順のまま） |
| システムが出す確認の画面（ツールの許可など） | 代行できない。人が答える |

代行しないもので止まったときも、決定のレポートの「時間」に、人の待ちとして書く（下の「計測」の「人の仲介が残った箇所」）。

## 置き場所とファイル

- 置き場所：リポジトリ直下の **`.decisions/`**。`.git/info/exclude` に入れてあり、**コミットしない**。
- 依頼：`.decisions/<連番>-<種類>-<対象>.request.md`
  - 連番は 3 桁。#22 の間は通しで振る（回ごとに 1 に戻さない）。司令役が、`.decisions/` にある最大の連番 ＋ 1 を使う（最初の往復の試しは `000`）。
  - 種類：`ping`（往復の試し）・`decision`・`final`・`commit`・`escalate`・`detector`
  - 対象：仕様の ID か段（例 `EV-ORD-203`・`stage1`）。英数字と `-` だけ。
- 答え：`.decisions/<連番>.answer.md`（代行役が書く）
- **書き方**：どちらも、同じフォルダに `<名前>.tmp` で書き終えてから、名前を変える（`mv`。書きかけを相手に読ませない）。
- 書いた依頼は書き換えない。問いを足すときは、新しい連番の依頼にする。答えを直すときは、代行役が `<連番>.answer.md` を消さずに、新しい連番の答えで「`<連番>` の答えを取り消す」と書く。

## 依頼の形

先頭に次の欄を書き、続けて本文を書く。

```
種類：decision
対象：<対象の仕様の名前>・ケース <n>（<フレームワーク>）・段 <n>
仕様：NorthwindDbSampleSpec@<版>（ブランチ <ブランチ名>）
決定のレポート：<パス> の 決定 <N>〜<M>
書いた時刻：<yyyy-MM-dd HH:mm:ss>（Get-Date）
```

| 種類 | 本文 |
| --- | --- |
| `ping` | 「往復の試し」の 1 行だけ |
| `decision`・`final` | 決定のレポートの節と同じもの（仕様の ID・背景・問い・選択肢（間引かない）・選択肢ごとの結果・推奨と理由・影響するケース・記録先）。レポートから写してよい。司令役が同時に人に聞いていたはずの決定は、1 つの依頼にまとめる |
| `commit` | 仕様のクローンで書き換えたファイル（`git -C <クローン> status --short` の出力）・足した `DEC-*`・コミット メッセージの案 |
| `escalate` | 論点の要約、レビュー役の指摘（そのまま）、実装役の報告の要点、往復の回数、司令役の推奨（続ける・止める） |
| `detector` | フックの出力（そのまま）、止まったコミットの差分の要点、`TESTING.md` 3・4 から書ける理由の候補と、書けない理由 |

## 答えの形

```
依頼：<連番>
決めた者：代行（OpenTouryoCodingAgentAssets のセッション <セッション ID>・<モデル ID>）
答えた時刻：<yyyy-MM-dd HH:mm:ss>
```

続けて、1 件ごとに次を書く。

- `決定 <N>：GO（<選択肢の番号>）` か、自由に書く文言。`final` では「人に回す」もある
- 理由と根拠（仕様の本文・HLD・`DEC-*` の ID と文）
- 推奨と同じか違うか（違うなら、どこが違うか）
- 仕様が決めていないことを、後で戻しやすい側に決めたときは「**要レビュー**」
- `commit` の答え：`記録済み：NorthwindDbSampleSpec@<版>（ブランチ <ブランチ名>。push 済み）`

代行役は **NOGO（仕様の本文を直すのを待つ）を答えない**。仕様の本文は意図して不完全なまま保つ（`LLD/Decisions.md`「読み方」）ので、本文に誤りがあると見たときも、
決定記録で決める選択肢（「定めない」を含む）を選び、「要レビュー」を付ける。

## 司令役がすること

1. **待つ**：依頼を書いたら、`Monitor` の until-loop で答えのファイルを待つ（例：`until [ -f .decisions/<連番>.answer.md ]; do sleep 30; done`）。
   **質問の道具（`AskUserQuestion`）に切り替えない。** `Monitor` が時間切れで終わったら、同じ待ちをもう一度始める。
   待つ間も、司令役の手順で「保留して進めてよい」とされていること（段 2 以降に出た決定の、影響しないケースなど）は進める。
2. **書き込む**：答えを、決定のレポートの「判断」の欄に写す。形：
   `GO（2。定めない）。<日付> に代行が選んだ（決めた者：代行（<セッション ID>・<モデル ID>）。依頼 <連番>）。推奨と違う。要レビュー`
   （「推奨と違う」「要レビュー」は、答えにあるときだけ）。
3. **決定記録の案**：記録先が `LLD/Decisions` の決定は、司令役の手順のとおり、仕様のクローンに案を書く。「出どころ」の欄の末尾に
   「決めた者：代行（<セッション ID>・<モデル ID>）」を書き、「要レビュー」の答えなら、それも書く。**クローンでブランチを切り替えない・コミットしない**（代行役がする）。
   案を書いたら依頼 `commit` を書く。答えの版で、司令役の手順「仕様の更新」を回す（版の差分が決定記録だけかを確かめるのは今までどおり）。
4. **時間**：依頼の「書いた時刻」と答えの「答えた時刻」を、決定のレポートの「時間」に「代行の待ち」として書く（人の判断の待ちとは分ける）。
5. **文脈が要約された・セッションが止まったとき**：続ける前に、このファイルを読み直し、`.decisions/` で答えの無い依頼を確かめて、その待ちから再開する。

## 代行役がすること（人のレビューのために書いておく）

- `Monitor` で `.decisions/` を見張り、答えの無い依頼が来たら答える。
- **推奨をそのまま通さない。** 仕様の本文・HLD・`LLD/Decisions` の `DEC-*`・作者の過去の判断（OpenTouryoCodingAgentAssets の `DevelopmentHistory.md` 4.4 節、これまでの決定のレポート）から決める。
  仕様が決めていないことは、後で戻しやすい側（多くは「定めない」）を選び、「要レビュー」を付ける。
- `commit` では、仕様のクローンの差分が決定記録（`LLD/Decisions/*.md` と `LLD/Decisions.md` の索引の件数）だけかを確かめてから、決定記録のブランチにコミットして push する。
  それ以外のファイルが変わっていたら、コミットせずに答えにそう書く。

## 計測（#22 の「1 回ごとに見ること」への追加）

終わりの報告（司令役の手順 7）と `Reporting.md` の振り返りに、次を書く。

- 代行に上げた判断の数（種類ごと）、そのうち推奨と違う答えの数、「要レビュー」の数
- 代行の待ちの合計（作業の時間と、人の判断の待ちとは分ける）
- 人の仲介が残った箇所と、その理由（取り決めの直しの材料）
