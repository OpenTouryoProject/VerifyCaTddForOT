# テスト先行：レビューの観点（出荷ステータス更新ダイアログ OrdTfShip）

**レビュー役が使う**（司令役が渡す）。段 1（テスト仕様）・段 2（Red）・段 4（Green）を承認する前に、ここと突き合わせる。
**実装役には読ませない**（読むと、仕様からテストを起こす力を確かめられない）。

どの対象にも共通の観点は [cmn-testfirst-review.md](./cmn-testfirst-review.md)（両方を使う）。
仕様の出どころは [spec/test3-testfirst-OrdTfShip.md](../spec/test3-testfirst-OrdTfShip.md)。段 1 のテスト仕様に、次が入っているか。

| 種類 | 観点 | 根拠 | 入っているべきケース（例） |
| --- | --- | --- | --- |
| B層 | 表示（未出荷） | `EV-ORD-401` 手順 1〜5、`ORD-T7` | 出荷日は当日、配送業者は `ShipVia`（無ければ未選択）、送料は `Freight`。在庫引落の内訳は明細ごとの商品名・数量・現在庫数で、`Quantity > UnitsInStock` の行が分かる。状況（未出荷・納期遅延）。`RowVersion` を返す |
| B層 | 表示（出荷済）・無い受注 | `EV-ORD-401` 手順 1・6 | 出荷日・配送業者・送料は DB の値、内訳は返さない（または表示しない）。無い受注 → NOTFOUND |
| B層 | 出荷の確定 | `EV-ORD-402` 手順 4・6、`OD-T5`、`PRD-T5` | 明細ごとに `UnitsInStock - Quantity`。`ShippedDate`・`ShipVia`・`Freight` の更新、`RowVersion` + 1。ちょうど 0 になる在庫は確定できる |
| B層 | 在庫不足 | `EV-ORD-402` 手順 4-2 | 1 行でも不足なら何も更新しない（受注・全部の商品の在庫）。「在庫が不足しています：〈商品名〉」で、不足の商品を全部列挙 |
| B層 | 出荷情報の更新（出荷済） | `EV-ORD-402` 手順 5 | 在庫は変わらない。出荷日・配送業者・送料だけ変わる |
| B層 | **表示時点の状態を信じない** | `EV-ORD-402` 入力・手順 3・4、`DEC-ORD-49`、[共通の観点](./cmn-testfirst-review.md) 段 1 | 画面が送る「表示時点の出荷済／未出荷の別」が DB の行（`RowVersion` が一致した行）と食い違う要求で、在庫の引き落としを外せない・二重に引き落とせない。期待が仕様で決まらないなら、仕様の決定に上げているか |
| B層 | 検証（まとめて） | `EV-ORD-402` 検証内容・手順 1、`ORD-T3` | 1 件でも違反なら更新しない。複数の違反は全部返る。必須（出荷日・配送業者）、日付、`受注日 <= 出荷日`（「出荷日は受注日以降を指定してください。」）、送料 >= 0、配送業者の存在 |
| B層 | 出荷の取消 | `EV-ORD-403` 手順 4〜6、`OD-T5` | 明細ごとに `UnitsInStock + Quantity`。`ShippedDate` は NULL、`ShipVia`・`Freight` は変わらない、`RowVersion` + 1。未出荷 → ERR-BIZ「この受注は出荷されていません。」で何も変わらない |
| B層 | 楽観排他 | `EV-ORD-402` 手順 3・6、`EV-ORD-403` 手順 3・6、`HLD/Common.md` 9.1 節 | 表示の後に他で更新 → CONFLICT、消された → NOTFOUND（区別）。どちらも在庫は変わらない（ロールバック）。確定と取消の両方 |
| E2E | 一覧から開く | `EV-ORD-108`、`SC-ORD-01-B04`、F-5 | 各行の「出荷更新」、出荷済の行は「出荷変更」。閉じた・確定した後に、同じ条件・ページ・並びで再検索され、行の状況が変わる |
| E2E | 詳細から開く | `EV-ORD-205`、`SC-ORD-02-B03` | 閉じた・確定した後に詳細が最新になる（出荷日・状況・編集の活性）。最新化の後の削除が CONFLICT にならない（`RowVersion` も更新される） |
| E2E | ダイアログの表示 | `EV-ORD-401`、`SC-ORD-04` の画面項目 | 未出荷：「出荷確定」が活性・出荷取消が非活性・内訳が出る・不足の行が強調。出荷済：「出荷情報を更新」・出荷取消が活性・内訳が出ない。配送業者は会社名の昇順 |
| E2E | 確定・更新・取消 | `EV-ORD-402` 手順 1・8、`EV-ORD-403` 手順 1・8 | 違反は全部のエラーでダイアログに留まる。成功で「受注 ID nnn の出荷情報を更新しました。」「受注 ID nnn の出荷を取り消しました。」。取消の確認で取り消すと何も変わらない |
| E2E | 閉じる | `EV-ORD-404` | DB は変わらない。変更がなくても呼び出し元を再読み込みする（他で変わった値が見える） |
| E2E | ボタンの配置 | 範囲の「前の回から引き継ぐこと」 | ダイアログのボタンの置き場所を、規約の解釈として仕様の決定に上げているか（推測で置いていないか）。一覧の `B04`・詳細の `B03` はフッタの外 |
| 共通 | テストのデータ | 範囲の「データを書き換えるテスト」 | 既存の受注・商品を書き換えない（出荷の確定・取消で在庫が動く）。終わりに既存の商品の在庫の合計を確かめる手順がある |
| 共通 | 前の回の約束 | 範囲の「前の回から引き継ぐこと」 | 一覧状態を書き換えない。前の回までの E2E（一覧・詳細・登録・編集）の期待を変えない（変えるなら期待値の変更） |
